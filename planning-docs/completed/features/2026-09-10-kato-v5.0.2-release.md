# Milestone: KATO v5.0.2 Release (PATCH)

**Completed**: 2026-09-10
**Type**: Release / Milestone (patch version bump)
**Impact**: Closes the release gap left open when the Multi-Worker Uvicorn + Concurrent Training Safety initiative completed on `main` (DECISION-026) without a matching published image — every image tagged before v5.0.2 still had the observe-path deadlock. No API change.
**Decision**: DECISION-027 in `planning-docs/DECISIONS.md`

## Summary

KATO v5.0.2 was released via `./container-manager.sh patch` (AUTO_MODE), bumping from 5.0.1 to 5.0.2. This ships the Multi-Worker Uvicorn + Concurrent Training Safety initiative's fixes to a published image for the first time: the observe-path deadlock fix (stopgap, then the Phase 1.6 lock-free refactor), clear-all residue fixes, a store-parity tool, the container `HEALTHCHECK` fix, one-writer-per-session docs with a strict xfail, and a perf/integrity test. The patch bump reflects that none of this changes any API contract — `KatoProcessor.learn` becoming a coroutine is an internal signature change, not an API-surface change.

The gap this closes: DECISION-026 closed the initiative on `main`, but the released v5.0.1 image (and everything before it) still had the original deadlock — any two overlapping observe requests for the same `node_id` would permanently hang a uvicorn worker. The deployment stack had been running an unreleased local `kato:latest` build with the fix rather than a published image. This release corrects that.

## Bump Rationale

**PATCH** — no API contract change. `KatoProcessor.learn` becoming a coroutine is internal to the processor, not an API-surface change. Contrast with v5.0.0's **major** bump (DECISION-022), which was forced by DECISION-019's breaking `anomalies`→`fuzzy_matches` prediction-field split. A minor bump (5.1.0, framing this as "multi-worker concurrency now safe and lock-free") was offered as an alternative in `pending-updates.md` given the deadlock's severity, but the user chose patch — consistent with this project's semver policy weighting API-contract impact over bug severity.

## Post-Release Finding + Fix: Topology Test Fragility (commit `61e16cd`)

Immediately after the deployment container restart, the topology suite showed 4 failures, then 1 on rerun (`test_session_count_converges_on_every_worker`: "expected count to return to 6 after deleting 5, got 1").

**Root cause**: test fragility, not a product bug. The active-session index (Redis `SET kato:session:_active_index`) is shared by every KATO process on the stack. The deployment container's own expiry sweep removed other (short-TTL, perf-run) sessions during the test's window, so the test's "global count == baseline ± 5" assertion only ever held on a quiet Redis — it was never actually asserting something true regardless of concurrent activity.

**Fix**:
1. The test now asserts membership of its own session ids in the active-session index — exact and correct regardless of unrelated churn from other processes.
2. In a quiet window found via bounded retry, it also asserts that every worker's `/sessions/count` equals the index cardinality read at the same instant (truth-at-the-same-instant, rather than an absolute before/after delta that assumes nothing else touches the shared counter).
3. Event-delivery timeout raised 5s → 10s — one timeout was observed during the deployment container's CPU-heavy startup window.

Topology suite 18/18 after the fix. See `planning-docs/project-manager/patterns.md` for the generalized testing-pattern entry this produced.

## Explicitly Not Part of This Release

The two new Phase-1.6-discovered follow-ups (auto-learned patterns not carrying session emotives/metadata; `vector_processor.deferred_vectors_for_learning` per-processor state on the legacy VI indexer path) remain open backlog items — see `planning-docs/SPRINT_BACKLOG.md`. Neither blocked this release; both are pre-existing behavior, not regressions introduced by the initiative.
