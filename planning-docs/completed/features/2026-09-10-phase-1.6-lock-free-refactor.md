# Phase 1.6: Lock-Free Per-Request Working State (Multi-Worker Uvicorn Initiative Closed)

**Completed**: 2026-09-10
**Commit**: `b155cb5` "refactor(workers): per-request working state through observe/learn/predict (Phase 1.6)"
**Decision**: DECISION-026 (`planning-docs/DECISIONS.md`); follows DECISION-025 (Option A stopgap) and DECISION-024 (concurrent-write limitation)
**Initiative**: Multi-Worker Uvicorn + Concurrent Training Safety — this phase closes the initiative

## Summary

Closed out the "Multi-Worker Uvicorn + Concurrent Training Safety" initiative by replacing the temporary `asyncio.Lock` stopgap (DECISION-025 Option A, commit `9de98c3`) with the originally-intended lock-free design (Option B): per-request working STM/emotives/metadata threaded explicitly through the observe/learn/predict call chain, instead of being staged into shared `pattern_processor` instance variables ("the BRIDGE pattern") for the duration of a request.

This is the completion of the stateless-processor architecture's original intent for these three code paths — flagged in `CLAUDE.md` as `BRIDGE:`/`TODO (Phase 1.6/1.7)` comments since the processor was made externally stateless, and shown by DECISION-025's deadlock investigation to be load-bearing for correctness, not just a stylistic cleanup.

## What Changed

### `kato/workers/pattern_processor.py`
- New stateless `learn_from(stm, emotives, metadata)` — takes explicit STM/emotives/metadata, returns the learned pattern name (or `""`), does not read or write `self.STM`.
- New stateless `predict_from(stm, unique_id, trigger_predictions)` — takes explicit STM, returns predictions without touching instance state.
- Legacy `learn()` and `processEvents()` remain as thin delegates over the processor's own `self.STM`, kept for backward compatibility with non-request callers that still use the old stateful API.

### `kato/workers/pattern_operations.py`
- New `learn_pattern_from(stm, emotives, metadata)` → `"PTRN|<hash>"` or `""`, the per-request counterpart to the existing stateful `learn_pattern`.

### `kato/workers/observation_processor.py`
- `process_observation(data, config, *, stm, emotives, metadata)` now operates on a per-request copy of STM and returns the updated `'stm'` in its result rather than mutating shared state.
- `check_auto_learning(stm, emotives, metadata, max_pattern_length, stm_mode)` → `(name, new_stm)`. CLEAR vs. ROLLING semantics are preserved exactly as before.

### `kato/workers/kato_processor.py`
- `observe`, `learn`, and `get_predictions` now pass `session_state` fields straight through to the stateless functions above instead of loading them into the processor's shared instance state first.
- The `_bridge_lock = asyncio.Lock()` stopgap added in `9de98c3` (DECISION-025 Option A) is **removed**. No `BRIDGE:` sections remain in this file.

### Tests
- `tests/tests/integration/test_worker_topology.py`: new `test_interleaved_sessions_keep_their_own_stm`, parametrized over `KATO_WORKERS` in {1, 2, 4}. The `workers=1` case is the deterministic same-processor-instance interleaving case — two sessions observing concurrently on a single worker process, which is exactly the scenario the old bridge pattern (and its lock, in both the deadlocking original and the DECISION-025 stopgap) existed to protect against. Each session must end with exactly its own STM.

### Docs
- `CLAUDE.md`: "Stateless Processor Architecture" section rewritten — the bridge pattern description is gone; replaced with "per-request working state," "no locks in the request path," and "one writer per session."
- `docs/architecture-decisions/ADR-001-stateless-processor.md`: history line added noting Phase 1.6 completion.
- `CHANGELOG.md`: `[Unreleased]` entry added.

## Behavior Preserved (One Pre-Existing Quirk Documented, Not Fixed)

**Auto-learned patterns are stored without the session's emotives/metadata.** This is not a regression introduced by this change — the old bridge pattern only ever loaded STM onto the shared `pattern_processor` for the observe path; emotives and metadata were never loaded there, so an auto-learn triggered from inside `observe` never had them available either. Phase 1.6 preserves this behavior exactly, and now states it explicitly in code at the auto-learn call site instead of leaving it an implicit side effect of what got bridged. Filed as a follow-up decision item, not fixed here — see `planning-docs/SPRINT_BACKLOG.md` Backlog.

## Verification

- **Worker-topology suite**: 18/18 passing, including the new interleaving test across `KATO_WORKERS` in {1, 2, 4}.
- **Perf/integrity test** (`KATO_PERF=1`, 8 threads × 10 rounds, `tests/tests/performance/test_multi_worker_throughput.py`): PASSED — speedup 1.83× (4 workers vs. 1), exact pattern counts, exact shared-pattern frequency, Redis/ClickHouse agreement, all workers still answering `/health` after the run, clean clear-all. (Under the DECISION-025 stopgap, this same test measured 1.15× while the full suite ran concurrently in the background — a noisy comparison; an isolated driver run under the stopgap separately measured 1.9×. Not a controlled apples-to-apples benchmark, but nothing observed suggests a throughput regression from removing the lock.)
- **Full suite**: 482 passed / 4 skipped / 1 xfailed / 0 failed (651s). Baseline immediately before this initiative began: 475 passed / 4 skipped / 0 failed. The single xfail is `test_concurrent_session_modifications`, the DECISION-024 documented limitation — unaffected by this change.
- **Store parity tool** (`scripts/check_store_parity.py`): 0 mismatched `kb_id`s after the run.
- Initiative verification list item 5 (the `kato-notebooks` `MAX_SAMPLES=10000` scale run, expecting 4-5×) remains a manual/optional step outside this repo; the in-repo perf/integrity test above is the accepted stand-in per the Phase C agreement (DECISION-025).

## Initiative Status: COMPLETE

All planned phases of "Multi-Worker Uvicorn + Concurrent Training Safety" are done:
- **Phase A** — data-integrity fixes (glob-escape, `clear_all_memory` async-flush ordering, parity tool) — `7aad817`
- **Phase B** — same-session concurrent-write limitation documented + strict xfail — `bef2b47`
- **Phase C** — throughput/integrity verification test; exposed and then (via A→B below) fixed the observe-path deadlock — `9de98c3` (stopgap), this phase (lock-free)
- **Phase D** — planning docs, this entry plus the SPRINT_BACKLOG.md/SESSION_STATE.md/DECISIONS.md updates accompanying it

Deployment note: the deployment stack currently runs the local `kato:latest` build (which has both the deadlock fix and Phase 1.6) via a gitignored compose override, not the released v5.0.1 image (which still has the original deadlock bug). A release is warranted — see `planning-docs/project-manager/pending-updates.md`.
