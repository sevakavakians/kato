# Milestone: KATO v5.2.0 Release (MINOR)

**Completed**: 2026-09-18
**Type**: Release / Milestone (minor version bump)
**Impact**: Ships pattern metadata fetched after top-K pruning (O(matched)→O(bounded) cost), a cross-worker statistics divergence fix, several determinism/leak/query-chunking fixes, and a round of security hardening. No API contract change.
**Decision**: DECISION-033 in `planning-docs/DECISIONS.md` (extends DECISION-032, the technical work this release ships)

## Summary

KATO v5.2.0 — "Deterministic prediction path and metadata fetched after pruning" — was released from branch `perf/prediction-path-scaling`, merged to `main` as `c67b2b6`. ## Bump Rationale

**MINOR** — per `docs/maintenance/releasing.md`, "Performance improvements" is classified as a MINOR bump (new capability/behavior improvement, backward-compatible). No API contract changed: `attach_pattern_metadata` is an internal pipeline restructuring, `stats_version` is invisible to API consumers, and the determinism/security fixes correct behavior without touching any documented interface. Contrast with v5.0.0's MAJOR bump (DECISION-022, a genuine breaking `anomalies`→`fuzzy_matches` field split) and every prior 5.x release's PATCH bumps (bug fixes with no capability change) — this release's scope (a structural performance win, not merely a bug fix) is what tips it to MINOR.

## Explicitly Not Part of This Release

- **Candidate-set bounding** (highest priority next item) — the default `filter_pipeline=[]` path still pulls every pattern in the node into Python per request (O(N) time/memory, no `LIMIT`). The user explicitly asked to discuss this separately, with measurements, before deciding an approach — see `planning-docs/project-manager/pending-updates.md`.
- **Phase 1c Step B** — skip building `Prediction` objects for candidates that will be pruned. Order-sensitive (`snr` uses pre-segmentation `extras`, `confidence` uses post-segmentation `present`); gated on the parity test reproducing that ordering exactly.
- **Phase 2** — remove `conditional_probability_cached` (up to 600 sequential Redis round trips per request to cache ~0.41ms of arithmetic).
- **Phase 3** — add a `--match-rate` axis and peak-memory reporting to `benchmarks/test_service_scaling.py`.
- **Longer term**: `query_points()` migration (blocked on qdrant-client >1.15); caching `PatternSearcher` between requests (depends on the candidate-set-bounding decision); synchronous ClickHouse/Redis clients blocking the event loop; the inaccurate code comment claiming RapidFuzz releases the GIL for the `_lcs_ratio_scorer` thread pool; `REDIS_PASSWORD`; dashboard hardening; `sort_symbols` session-override bug; 25 `pytest.skip` calls; unbounded request payloads; authentication (deferred — trusted-network-only deployment).

All carried forward in `planning-docs/SPRINT_BACKLOG.md`.
