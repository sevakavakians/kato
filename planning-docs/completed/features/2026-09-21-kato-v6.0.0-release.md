# Milestone: KATO v6.0.0 Release (MAJOR)

**Completed**: 2026-09-21
**Type**: Release / Milestone (major version bump)
**Impact**: Ships the recall-safe candidate bound — a lossless necessary-condition predicate pushed into ClickHouse that bounds the default full-corpus candidate pull without ever running KATO's scorer there. Removes `length_min_ratio`/`length_max_ratio`/the `'length'` filter and rejects `recall_threshold=0` — two silent breaks for callers using them, hence the MAJOR bump.
**Decision**: DECISION-035 in `planning-docs/DECISIONS.md` (technical work: DECISION-034)

## Summary

KATO v6.0.0 merges and releases `perf/recall-safe-candidate-bound` (merge commit `51f8213`), closing out the candidate-set-bounding discussion the user requested after v5.2.0 shipped. This was previously recorded in planning-docs as complete-and-verified but unmerged — as of this release it is merged, released, and deployed.

The technical content of this release is **DECISION-034** and `planning-docs/completed/optimizations/2026-09-21-recall-safe-candidate-bound.md` — not repeated here in full. Summary for continuity: ClickHouse has no LCS function and cannot run KATO's actual scorer (`_lcs_ratio_scorer`), so a **necessary-condition predicate** (a length window plus a token-overlap count, both computable by counting on stored `length`/`token_set` columns) is pushed into the ClickHouse query instead — provably never smaller than the true similarity, so it can only drop patterns that cannot possibly pass `recall_threshold`. ClickHouse never decides MATCH, only CANNOT; every survivor still runs the unchanged Python scorer, so prediction output is byte-identical. Shipped on by default (`KATO_RECALL_BOUND_ENABLED`, default `true`); `LengthFilter` deleted entirely (it was recall-unsafe, not just imprecise); `recall_threshold=0` rejected everywhere.

## Bump Rationale

**MAJOR**, user-chosen from a recommendation. `docs/maintenance/releasing.md` lists "Remove configuration parameters" as an explicit MAJOR trigger, and this release does exactly that — `length_min_ratio`, `length_max_ratio`, and the `'length'` filter pipeline name are all removed. Separately, `recall_threshold=0` was previously valid input and is now rejected outright. Both are silent breaks for any deployment currently passing those parameters or that value: a config that validated cleanly under v5.2.0 fails under v6.0.0.

This is a **deliberate reversal of the v5.2.0 precedent** (DECISION-033), where the user chose MINOR over a MAJOR recommendation for a release that was structurally significant but did not change the configuration surface's validity — there, "no API contract change" carried the decision. Here, the documented "remove configuration parameters" trigger applied literally, and the user went with the literal reading instead. Worth recording as a contrast pair — see DECISION-035 for the full discussion. Neither approach is "the rule"; each release gets its own read against `docs/maintenance/releasing.md`'s criteria.

## Process Note — An Unverified Claim in the Published Release Notes (self-caught, corrected)

The release notes as first published claimed the `filter_pipeline` rejection came "with a message naming the filter." **This was asserted without testing and was false**: the create path actually returned 422 citing `recall_threshold` (a misleading example, not the actual problem), and the update path returned 400 saying "see server logs." Caught during post-release verification, not before publishing.

The published GitHub release notes and `CHANGELOG.md`'s v6.0.0 entry were corrected to describe the actual (generic-message) behavior — `CHANGELOG.md` now carries an explicit blockquote noting the message is generic in 6.0.0 and improved in 6.0.1, so the historical record stays accurate rather than being silently rewritten. The underlying defect was fixed same-day in **v6.0.1** — see `planning-docs/completed/features/2026-09-21-kato-v6.0.1-release.md`.

This is logged as a process pattern in `project-manager/patterns.md`: a claim written into user-facing release notes without being exercised at all, adjacent to but distinct from the "verification that could not have failed" family of findings already logged there.
