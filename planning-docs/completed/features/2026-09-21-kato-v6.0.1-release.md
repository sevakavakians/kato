# Milestone: KATO v6.0.1 Release (PATCH)

**Completed**: 2026-09-21 (same day as v6.0.0)
**Type**: Release / Bug Fix (validation gap) + Standing Rule Application
**Impact**: Fixes a `filter_pipeline` validation gap that was the single most likely v6.0.0 upgrade failure mode — both create and update session-config paths now return HTTP 400 naming the offending filter and listing valid ones, instead of a generic or actively misleading message. Also applies a new standing project rule, established this session, that runtime messages must never carry deprecation/removal commentary — now enforced by an automated test.
**Decisions**: DECISION-036 (release + validation fix), DECISION-037 (new standing rule) in `planning-docs/DECISIONS.md`

## Summary

Within hours of releasing v6.0.0, post-release verification found that `filter_pipeline` — a config field v6.0.0 itself made more consequential by removing the `'length'` filter — was never validated by `ConfigurationService` at all. A rejection fell through to `SessionConfiguration.validate()`, which returns a bare `False` with no field-level detail; the create path's fallback message even cited `recall_threshold` as an example field, actively misleading anyone whose real problem was an unknown filter name. Any deployment still passing `filter_pipeline=['length']` on upgrading from v5.2.0 would hit exactly this gap.

Drafting the fix's rejection message surfaced a second, independent issue: the first draft included commentary about why `'length'` was removed and when — which the user explicitly rejected as a standing rule violation (see DECISION-037 below). Both issues were fixed in this same-day patch release.

## What Changed

### (a) `filter_pipeline` Validation Fix

- Both `POST /sessions` (create) and `POST /sessions/{id}/config` (update) now return HTTP 400 naming the offending filter(s) and listing the valid ones, instead of a generic/misleading message.
- `VALID_FILTERS` hoisted to a single shared constant in `kato/sessions/session_config.py` — previously duplicated between the two validators, which is exactly what let them disagree about which filter names are accepted.
- New regression test: `test_unknown_filter_is_rejected_naming_the_filter` (`tests/tests/unit/test_session_config.py`).

### (b) New Standing Rule — DECISION-037: No Deprecation/Removal Notes in Runtime Messages

**Never include information or notes on deprecated or removed functionality in KATO's runtime messages.** Error messages, API response bodies, and log lines state the CURRENT requirement only — what changed, when, and why belongs in `CHANGELOG.md`, never in code or the API.

Triggered by a message drafted this session:

> "Unknown filter(s): 'length'. Valid filters: minhash, jaccard, bloom, rapidfuzz. The 'length' filter was removed in 6.0.0 because it discarded patterns that genuinely matched; remove it from the pipeline. Candidate bounding is now automatic and needs no configuration."

The second sentence onward was the violation. The user's own words: *"Never include information or notes on deprecated functionality in KATO's messages... All of that information should only be in the changelogs, rather than as part of the code or API."*

**Five messages corrected** (1 new this session, 4 pre-existing), each keeping the actionable half and dropping the commentary:

| Message | Before | After |
|---|---|---|
| `filter_pipeline` rejection | (drafted with deprecation commentary, never shipped that way) | Names the filter, lists valid ones, nothing more |
| Session rehydration warning | "no longer valid" | "outside the permitted range (> 0.0 and <= 1.0)" |
| `getPatterns()`/`getPatternsAsync()` `RuntimeError`s | "is deprecated. Hybrid architecture uses..." | "is not supported. Pattern loading runs through..." |
| `symbols_kb.update_one()` log warning | "called but is deprecated in hybrid architecture" | "is a no-op; use `increment_symbol_frequency` or `increment_pattern_member_frequency`" |
| `/percept-data`/`/cognition-data` response `warning` field | "This endpoint is deprecated. Use /sessions/..." | "Use /sessions/{session_id}/percept-data for session-aware data." |

The `/percept-data`/`/cognition-data` `warning` field itself is kept (no schema change), and both endpoints keep their OpenAPI `deprecated: true` flag — that flag is structured metadata, not prose commentary, and is outside this rule's scope.

**Enforced by test, not just documented**: `test_unknown_filter_is_rejected_naming_the_filter` fails if a runtime message contains `"deprecat"`, `"removed in"`, `"was removed"`, `"no longer"`, `"superseded"`, or a version-number pattern — a machine-checked guard against reintroducing this class of message going forward.
